EcoRPA enforces rate limits on all API requests to keep the platform stable and performant for every user. Understanding how these limits work — and writing your integration to respect them — prevents disruptions and ensures your workflows continue running reliably. This page explains the limit tiers, the headers EcoRPA returns on every response, and how to handle the `429 Too Many Requests` error gracefully.

## Rate Limit Tiers

Your rate limit depends on the plan associated with your EcoRPA account. The following quotas apply per API key.

| Plan | Requests / Minute | Requests / Day |
|---|---|---|
| Free | 60 | 1,000 |
| Pro | 600 | 50,000 |
| Enterprise | Custom | Custom |

If you need higher limits, [upgrade your plan](https://app.ecorpa.com/billing) or contact the EcoRPA sales team to discuss an Enterprise arrangement with limits tailored to your traffic profile.

## Rate Limit Headers

EcoRPA includes three headers in every API response so you can monitor your usage programmatically without waiting for a `429` error.

| Header | Type | Description |
|---|---|---|
| `X-RateLimit-Limit` | integer | The maximum number of requests allowed in the current window for your plan. |
| `X-RateLimit-Remaining` | integer | The number of requests you can still make before the limit resets. |
| `X-RateLimit-Reset` | integer | A Unix timestamp (UTC) indicating when the current window expires and your quota refreshes. |

Here is an example response showing these headers:

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-RateLimit-Limit: 600
X-RateLimit-Remaining: 543
X-RateLimit-Reset: 1705312860
```

You can convert `X-RateLimit-Reset` to a human-readable time using any Unix timestamp converter, or handle it directly in code:

```python
import datetime

reset_timestamp = 1705312860
reset_time = datetime.datetime.utcfromtimestamp(reset_timestamp)
print(f"Rate limit resets at {reset_time} UTC")
```

## Handling 429 Errors

<Warning>
  When you exceed your rate limit, EcoRPA returns a `429 Too Many Requests` status. At this point, EcoRPA stops processing new requests from your API key until the current window resets. Do not retry immediately — doing so prolongs the throttled state and wastes your remaining quota in the next window.
</Warning>

The `429` response body includes a machine-readable error and the `Retry-After` header, which tells you exactly how many seconds to wait before retrying:

```json
{
  "error": {
    "code": "rate_limit_exceeded",
    "message": "You have exceeded your request limit. Please retry after the reset window.",
    "retry_after": 34
  }
}
```

The safest way to handle `429` errors is exponential backoff with jitter: wait progressively longer between retries, and add a small random delay to prevent multiple clients from hammering the API in lockstep.

```python
import time
import random
import requests

ECORPA_API_KEY = "your_api_key"  # Use an environment variable in production
BASE_URL = "https://api.ecorpa.com/v1"
MAX_RETRIES = 5

def get_workflows():
    headers = {"Authorization": f"Bearer {ECORPA_API_KEY}"}

    for attempt in range(MAX_RETRIES):
        response = requests.get(f"{BASE_URL}/workflows", headers=headers)

        if response.status_code == 200:
            return response.json()

        if response.status_code == 429:
            # Respect Retry-After if present, otherwise use exponential backoff
            retry_after = int(response.headers.get("Retry-After", 0))
            backoff = retry_after or (2 ** attempt)
            jitter = random.uniform(0, 1)
            wait = backoff + jitter

            print(f"Rate limited. Retrying in {wait:.2f}s (attempt {attempt + 1}/{MAX_RETRIES})...")
            time.sleep(wait)
            continue

        # For non-429 errors, raise immediately
        response.raise_for_status()

    raise RuntimeError("Max retries exceeded. Could not complete the request.")
```

This pattern respects the `Retry-After` header when present, falls back to exponential backoff when it is not, and gives up after a configurable maximum number of attempts.

<Tip>
  Check `X-RateLimit-Remaining` in your response headers proactively rather than waiting for a `429`. If the value drops close to zero, introduce a deliberate pause in your request loop or switch to batched operations to stay within your quota window.
</Tip>
