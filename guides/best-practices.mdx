Building a reliable integration with EcoRPA goes beyond making API calls that work in a happy path. Production integrations handle failures gracefully, protect credentials, avoid duplicating data, and stay efficient under load. The practices below reflect hard-won lessons from real-world API integrations — follow them from the start to save yourself significant debugging time later.

<AccordionGroup>
  <Accordion title="Use Environment Variables for API Keys">
    Never hard-code your API key directly in source code. Hard-coded credentials are easy to accidentally commit to version control or expose in logs, and rotating them requires a code change and a deployment.

    Instead, load your API key from an environment variable at runtime:

    ```python
    import os
    import requests

    API_KEY = os.environ["ECORPA_API_KEY"]
    headers = {"Authorization": f"Bearer {API_KEY}"}
    ```

    For local development, use a `.env` file together with a library like `python-dotenv` or `dotenv` for Node.js, and add `.env` to your `.gitignore`:

    ```bash
    # .env  (never commit this file)
    ECORPA_API_KEY=your_key_here
    ```

    In production, store secrets in a dedicated secrets manager such as AWS Secrets Manager, HashiCorp Vault, or your hosting provider's built-in secret store. This makes rotation straightforward and keeps credentials out of your codebase entirely.
  </Accordion>

  <Accordion title="Implement Exponential Backoff">
    Transient failures are a normal part of any distributed system. When you receive a `429 Too Many Requests` or any `5xx` server error, do not retry immediately — rapid retries amplify load and worsen the problem.

    Instead, implement exponential backoff with jitter: start with a short wait, double it on each subsequent failure, and add a small random offset to prevent synchronized retries across multiple clients.

    ```python
    import time
    import random
    import requests

    def request_with_backoff(url, headers, max_retries=5):
        for attempt in range(max_retries):
            response = requests.get(url, headers=headers)

            if response.status_code in (200, 201):
                return response.json()

            if response.status_code in (429, 500, 502, 503, 504):
                wait = (2 ** attempt) + random.uniform(0, 1)
                print(f"Attempt {attempt + 1} failed ({response.status_code}). Retrying in {wait:.2f}s...")
                time.sleep(wait)
                continue

            response.raise_for_status()  # Raise for non-retriable errors immediately

        raise RuntimeError("Max retries exceeded.")
    ```

    Only retry on retriable status codes (`429`, `500`, `502`, `503`, `504`). Do not retry `4xx` errors other than `429` — those indicate a problem with your request that retrying will not fix.
  </Accordion>

  <Accordion title="Use Idempotency Keys">
    Network failures can leave you unsure whether a `POST` request succeeded. Without idempotency keys, retrying a failed request risks creating duplicate workflows, tasks, or other resources.

    EcoRPA supports the `Idempotency-Key` header on all `POST` endpoints. Pass a unique key (a UUID works well) with each create request. If EcoRPA receives a second request with the same key within 24 hours, it returns the original response instead of creating a duplicate.

    ```python
    import uuid
    import requests
    import os

    API_KEY = os.environ["ECORPA_API_KEY"]

    def create_workflow(name, description):
        idempotency_key = str(uuid.uuid4())

        response = requests.post(
            "https://api.ecorpa.com/v1/workflows",
            headers={
                "Authorization": f"Bearer {API_KEY}",
                "Content-Type": "application/json",
                "Idempotency-Key": idempotency_key,
            },
            json={"name": name, "description": description},
        )
        response.raise_for_status()
        return response.json()
    ```

    Store the idempotency key alongside the request in your own database so you can reuse the same key on retry rather than generating a new one. Generating a new key on every attempt defeats the purpose.
  </Accordion>

  <Accordion title="Paginate Large Datasets">
    EcoRPA caps the number of results returned in a single response (typically 20–100 items). Never assume the first page contains every record — always paginate to retrieve complete datasets.

    Use the `page` and `per_page` query parameters and continue fetching until the response indicates there are no further pages:

    ```python
    import requests
    import os

    API_KEY = os.environ["ECORPA_API_KEY"]

    def get_all_workflows():
        all_workflows = []
        page = 1

        while True:
            response = requests.get(
                "https://api.ecorpa.com/v1/workflows",
                headers={"Authorization": f"Bearer {API_KEY}"},
                params={"page": page, "per_page": 100},
            )
            response.raise_for_status()
            body = response.json()

            all_workflows.extend(body["data"])

            meta = body.get("meta", {})
            if page >= meta.get("total_pages", 1):
                break

            page += 1

        return all_workflows
    ```

    Be mindful of rate limits when iterating through large datasets. Consider adding a short delay between pages or processing data incrementally rather than loading everything into memory at once.
  </Accordion>

  <Accordion title="Validate Webhook Signatures">
    Your webhook endpoint is publicly reachable by definition, which means anyone on the internet can send it a POST request. Without signature validation, a malicious actor could forge payloads and trick your system into taking unintended actions.

    Always recompute the HMAC-SHA256 signature using your webhook secret and compare it to the `X-EcoRPA-Signature` header before processing any payload:

    ```python
    import hmac
    import hashlib
    import os
    from flask import Flask, request, abort, jsonify

    app = Flask(__name__)
    WEBHOOK_SECRET = os.environ["ECORPA_WEBHOOK_SECRET"]

    @app.route("/hooks", methods=["POST"])
    def webhook():
        raw_body = request.get_data()
        received_sig = request.headers.get("X-EcoRPA-Signature", "")
        expected_sig = "sha256=" + hmac.new(
            WEBHOOK_SECRET.encode(), raw_body, hashlib.sha256
        ).hexdigest()

        if not hmac.compare_digest(expected_sig, received_sig):
            abort(403)

        # Safe to process the payload now
        return jsonify({"ok": True}), 200
    ```

    Use a constant-time comparison function to prevent timing attacks. See the [Webhooks guide](/guides/webhooks) for a full implementation in both Python and Node.js.
  </Accordion>

  <Accordion title="Handle Errors Gracefully">
    EcoRPA returns structured error objects that give you everything you need to diagnose problems programmatically. Every error response follows this shape:

    ```json
    {
      "error": {
        "code": "resource_not_found",
        "message": "No workflow with the specified ID exists in your account.",
        "request_id": "req_01hxyz1234abcd"
      }
    }
    ```

    In your code, inspect `error.code` to determine the appropriate recovery action — for example, surface a user-friendly message for `resource_not_found` but alert your on-call team for `internal_server_error`.

    ```python
    response = requests.get(url, headers=headers)

    if not response.ok:
        error = response.json().get("error", {})
        code = error.get("code")
        request_id = error.get("request_id")

        print(f"API error [{code}] — request_id: {request_id}")

        if code == "resource_not_found":
            return None  # Handle gracefully
        else:
            raise RuntimeError(f"Unexpected API error: {code} (request_id: {request_id})")
    ```

    Always log the `request_id` value when you encounter an unexpected error. When you contact EcoRPA support, providing the `request_id` allows the support team to find the exact request in their logs instantly, which dramatically speeds up diagnosis.
  </Accordion>

  <Accordion title="Cache Infrequently Changing Data">
    Some EcoRPA resources — such as integration lists, account configurations, and plan details — change rarely but get read often. Fetching them on every operation wastes quota and adds latency to your integration.

    Cache these resources locally with a reasonable TTL (time-to-live) and refresh them in the background rather than on every request:

    ```python
    import time
    import requests
    import os

    API_KEY = os.environ["ECORPA_API_KEY"]

    _integrations_cache = {"data": None, "expires_at": 0}
    CACHE_TTL = 300  # 5 minutes

    def get_integrations():
        now = time.time()
        if _integrations_cache["data"] and now < _integrations_cache["expires_at"]:
            return _integrations_cache["data"]

        response = requests.get(
            "https://api.ecorpa.com/v1/integrations",
            headers={"Authorization": f"Bearer {API_KEY}"},
        )
        response.raise_for_status()
        data = response.json()["data"]

        _integrations_cache["data"] = data
        _integrations_cache["expires_at"] = now + CACHE_TTL
        return data
    ```

    For multi-instance deployments, use a shared cache layer such as Redis so all instances benefit from the same cached data rather than each making independent API calls. Avoid caching mutable resources like individual workflow states, where stale data could cause incorrect behaviour.
  </Accordion>
